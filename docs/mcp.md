# Working from an MCP client

`otea mcp` serves the agent commands as tools of a [Model Context Protocol](https://modelcontextprotocol.io) server on stdin and stdout, so an agent can work Otea without shelling out. Otea works the same with any harness, so it writes no harness's config: the agent adds the server to its own, from one instruction that `otea connect` prints.

```sh
cd /path/to/your/project
otea connect --as claude-b --model claude-opus-5-5 --effort high   # or just otea connect
otea connect --check --as claude-b                                 # was it heard over MCP?
```

- `otea connect` adds (or refreshes) Otea's block in `AGENTS.md` at the top of the checkout it runs in (a linked worktree's own, so agents working there read it), the guide most harnesses read (one that doesn't imports it from the file it reads), and prints the MCP server to add: named `otea`, a local stdio server that runs `otea mcp --project <id>` when the `otea` on your `PATH` is the same install as the one running `connect` (through `cmd /c` on Windows, where `otea` is npm's `.cmd` shim), so the config survives a checkout that moves. When no `otea` is on `PATH`, or the one there is another install, it prints the absolute form of the Otea running instead, with one warning line naming the `otea` on `PATH` (`node --disable-warning=ExperimentalWarning /path/to/otea/src/cli/main.ts mcp --project my-app-k3x7qa` from a checkout, `dist/cli/main.js` from the npm package, the desktop app's own Electron with `ELECTRON_RUN_AS_NODE=1` from the app); with `OTEA_HOME` when you set one. It prints it as fields and as JSON, and `--json` gives it as `mcp`. The JSON is one shape (`command`, `args`, `env`): the agent translates it to its harness's schema, or uses the harness's own `mcp add`, for this project only, never in its user or global config, since the server is pinned to the project (Claude Code: `.mcp.json`, or `claude mcp add --scope local`; OpenCode: an `mcp` entry in the project's `opencode.json`, with `command` as one array and `environment` for `env`; any other: its per-project MCP settings), then restarts or reloads the session if the harness needs it, approves the server if asked, and runs `otea connect --check`.
- The block in `AGENTS.md` holds no copy of the guide: it says the guide is the server's instructions, and that `otea board` (the `board` tool with no name) prints it for an agent on the command line or whose client shows no instructions.
- The server names no agent: each session names itself on every call (`as`), so two terminals in one folder never share a name. `--project <id>` pins it to the project: from a folder of another project it refuses to write (exit 7, `forbidden`, naming both), and started outside any project (a harness config kept for every folder) it serves the pinned one. `OTEA_PROJECT_ID` in the environment pins the CLI the same way.
- With `--as`, `connect` also declares the profile that agent runs as (`--model`, `--effort` and `--harness`; one it is not given stays as the agent declared it, else `unknown`, which the agent replaces in its first session; see [The profile an agent runs as](working-with-agents.md#the-profile-an-agent-runs-as)) and notes that it asked for MCP. Until that agent is heard through the MCP server, the desk's agents menu flags it **MCP sin conectar** (MCP not connected): its harness declined the server (Claude Code, for one, asks before it loads a project's server) or it was never added. It still works through the `otea` command meanwhile.
- `otea connect --cli` (or `--no-mcp`) is for an agent that works from the command line only: it still adds the `AGENTS.md` block and declares the profile, but prints no MCP server (a few lines, no PATH warning, nothing in `--json` as `mcp`) and does not note that the agent asked for MCP, so the desk never flags it **MCP sin conectar**.
- `otea connect --check` says whether the agent `--as` names (or, without it, any agent) was heard through the MCP server, and when, or else whether its harness (any, without `--as`) loaded the server, which counts too, since the agent may keep to the otea command; it exits 11 (`not_connected`) when none was, saying what to do.
- An older `otea connect` wrote an `otea` entry with `--as` into `.mcp.json`, which gave every session there one name; `connect` points at it so you remove it.
- The name is a short slug: at most 40 lowercase letters, digits and single dashes, starting with a letter, and not `you`, `human` or `agent`. Anything else fails with exit 6 (`invalid_agent_name`) and writes nothing. The web UI shows each agent by a mark derived from its name, so a stable name keeps its mark stable.
- One agent keeps one name across sessions: `otea whoami` (the `whoami` tool) gives a new session the name an agent of the same harness worked under from the same folder (or one inside or around it), while no session works under it now (a lease keeps a name busy only while its session is alive: a process it listens through still beats, or it made an otea call within the listening window, 150 s; the name of a session that ended holding an item is given back with the items it holds, for the new session to carry on); with none, it says to pick a new name, never one connected now, so a second terminal never takes another's. The name it gives is handed to that session for 5 minutes: two sessions started together are told distinct names (the second gets a free one of the same stem, such as `ana-2`), and a session refused a name (`name_in_use`) is told a free one the same way. The CLI names its harness with `--harness` (written any way: `Claude Code`, `claude-code` and `OpenCode 1.4` match `claude-code` and `opencode`); an MCP client names its own. A name whose profile names the harness comes first, then one with a profile, then one with none; a name declared for `cli` (a test name) is never given to a session of another harness. A server started under a name (`otea mcp --as ana`) is that agent's: a call as another agent is refused (exit 7, `forbidden`), and its subagents call as `ana-<role>`.
- A harness that loads the server and never calls it (a background service, a session that never uses Otea) shows as no agent: an agent is heard from its first call.
- On initialize the server gives Otea's agent guide as its `instructions`, which clients such as Claude Code put in the agent's context, in the words of the tools (`next { claim: true }`, not `otea next --claim`): the same text the `board` tool gives, since a client that reads only the instructions has no shell to run a command line in.
- Tools: `board`, `board_draft`, `list`, `show`, `create`, `update`, `attach`, `detach`, `link`, `unlink`, `next`, `reply`, `merged`, `reopen`, `tick`, `topic_add`, `topic_answer`, `topic_list`, `topic_show`, `ask`, `handoff`, `drop`, `approve`, `send_back`, `move`, `claim`, `profile`, `heartbeat`, `release`, `relay`, `events` and `wait`, one per agent command, named after it with words joined by underscores (`otea send-back` is `send_back`, `otea board draft` is `board_draft`). What a tool answers names the tools too: `otea claim TAR-1` in a text, or in `show`'s `hint`, reads `claim { id: "TAR-1" }`. Each takes that command's arguments and options by name (`{"id": "TAR-1", "note": "what changed"}`, `"field": ["Prioridad=Alta"]`, durations as `"90s"`, `"15m"`, `"1h"`, and `wait`'s `timeout` also as a number of seconds; a parameter's name is its option's with underscores for hyphens, as `topic_list`'s `all_projects` (the old hyphenated name still works; a key a tool does not take is refused by name, never dropped); `attach` takes `file` as a path the server reads, relative to the directory it runs in, and `module` by the part's name as `show` lists it or by its kind; `board_draft` takes the board JSON itself as `definition`, an object or a string, since a tool call has no stdin to pipe it on and no file is needed) and runs the command itself, so the rules, the validations and the error codes are those of the CLI. Setup and human commands (`init`, `brief`, `stats` (how each model performs is the person's reading), `projects`, `migrate`, `connect`, `collection icon`, `board add`, `validate`, `check`, `hook`, `serve`, `open`, `devices`, `mcp`) stay in the CLI, and `human-ui` moves are refused (`forbidden`) as in the CLI.
- A tool returns the text the command prints, in the words of the tools, as its one text content (no `structuredContent`, which some clients put in context beside the text, so the same fields would cost twice: +34% to +107% on `show`, `next` and a work cycle). `show` gives the item's fields as one JSON object line, `fields: {"Branch":"…","PR":"…"}`, which a model parses, in place of `name: value` lines, and `next` the same under `Starts with`. A write answers in a line, as on the CLI, not with the whole item; `events` gives one event a line, its id first. A failure is a tool error whose text is the CLI's message. Text costs an agent far fewer tokens than the item as JSON. A program that reads the data starts the server with `otea mcp --json`: each tool then returns the JSON the command prints with `--json`, `events` its events as one array, and a failure the same `{"error":{"code","message"}}`.
- One board's text leaves out Otea's agent guide, which the server's `instructions` already gave; the index (`board` with no name) opens with it, for a client that shows no instructions.
- `wait` gives up after 5 minutes unless `timeout` says otherwise, and refuses more than 15 minutes, since clients time out long tool calls. Giving up is a normal result (`isError: false`, text starting `Nothing arrived (this is not an error)`; under `otea mcp --json`, `{"timedOut":true,"message":"…"}`), not an error: call it again to keep waiting. The CLI keeps exit 13 (`timeout`). A cancelled call stops waiting. `events` has no `follow`: call it again with the last event id as `since`.
- Every tool takes `as`, the name of the agent making the call, and requires it (in the tool's schema) unless the server was started under a name; `whoami`, `topic_list` and `topic_show` never need one. Without it the call acts as the agent the server was started as (`otea mcp --as`, or `$OTEA_AGENT`). A server started with a name refuses a call under that name once a newer session of the same harness took it (`name_in_use`). A new server takes a name another open server works under only on its first call under it, and only when its harness no longer talks to the old one: the same harness process started both, or the client names the same harness as the agent's, the old server has served no tool call since the new one started, and it holds no wait open (a harness that starts each server through a shell of its own and leaves the old one running when it reloads its config). Any other second session under the name is refused and told a free one. Subagents share their parent's server, so each one passes its own `as` on every call: otherwise they sign with one name and take over each other's leases. A server started without a name refuses a call without `as` (the schema requires it; `unnamed_agent` for a client that skips the schema). The name rule is the CLI's (`invalid_agent_name`). The project is found from the directory the client starts the server in. Nothing but the protocol goes to stdout.
