# Working with agents

## Using it

With `otea` on your PATH (see [Install](../README.md#install)), run it inside the project you want to track:

```sh
cd /path/to/your/project
otea start                                 # for you, once: the project, a first board (--template <key>), the desk in the background and the text for your agent; run again, it reports what exists. An agent never runs it
otea init                                  # a new project starts with no board: pick them here or in Studio
otea init --template changes               # Cambios, the changes you ask an agent for (templates below; none for no board)
otea board add Errores --template bug-reports   # another board, from a template, published at once (yours: no agent name)

# What an agent runs: every command that acts names the agent (--as, or OTEA_AGENT for the session)
otea whoami --harness claude-code          # a new session: the name it worked under here before, if any
export OTEA_AGENT=claude
otea profile --model claude-opus-5-5 --effort high --harness claude-code   # what it runs as (unknown if it cannot tell)
otea create --collection Cambios --title "Write the docs" --field "Qué quiero=Install and first steps" --field "Cómo lo valido=Follow it on a clean machine"
otea create --collection Cambios --title "Fix the footer" --field "Qué quiero=It shows last year"   # no Cómo lo valido: starts in Aclarar
otea list --turn agent --unclaimed --json # waiting for agents and not held by another one
otea next                                  # which item to take now, and what its step asks
otea claim CAM-2                           # hold it for 15 minutes (--ttl 30m for another length)
otea heartbeat CAM-2                       # extend the lease on long work
otea handoff CAM-2                         # refused (exit 8) while what Aclarar asks for is missing
otea update CAM-2 --field "Cómo lo valido=The footer shows this year" --field "Clase de cambio=Error"   # fill what was missing
otea handoff CAM-2                         # on to Hacerlo; then otea next again
otea list --field "Clase de cambio=Error"  # items whose field holds that value, by name or id (repeat to AND them)
otea list --sort order                     # on top first, then the order fixed on the Matrix (numbered over open items), then the other open items, closed ones last
otea wait --turn agent --unclaimed         # nothing to do: block until there is something, then otea next
otea check --gate push --branch --repo     # may this branch be pushed? exit 0 yes, 19 no (fails open)
unset OTEA_AGENT
otea list                                  # read without a name: list, show, events and board need none
otea show CAM-1                            # what to do next, fields, moves the agent can relay, lease, timeline
otea validate                              # check boards, collections and items

otea hook install --git --forge            # in a repo: a pre-push hook, and GitHub rules on the protected base
otea help                                  # every command, global options and exit codes
```

## What your harness must allow

An agent follows Otea's flow with a few commands that a harness may stop to ask about, or block outright in a mode that judges each command itself. In one run, a harness's automatic mode blocked `git push` and `git worktree add`, and the agents stalled mid-step. For this project, allow:

- `otea`: its commands, and the tools of its MCP server when the agent uses them;
- `git push` to the items' branches. Otea's pre-push hook (`otea hook install --git`) still checks each push against the boards, so allowing the command doesn't let an agent past a gate;
- `git worktree add`, for an agent that works in its own worktree.

Otea writes no harness config. Add the rules to your harness's own project settings, in whatever syntax it uses. Two examples (check your harness's documentation for its current syntax):

- Claude Code, `.claude/settings.json`:

  ```json
  { "permissions": { "allow": ["Bash(otea *)", "Bash(git push *)", "Bash(git worktree add *)", "mcp__otea"] } }
  ```

- OpenCode, `opencode.json`:

  ```json
  { "permission": { "bash": { "otea *": "allow", "git push *": "allow", "git worktree add *": "allow" } } }
  ```

`otea connect` says the same in one line.

Agents claim an item before working it. A lease is atomic: while one agent holds an item, `otea claim`, `otea update` and `otea move` from any other agent fail with exit code 12 (`lease_held`), and `otea heartbeat` or `otea release` by someone who does not hold it fail with exit code 12 (`not_lease_holder`), saying who holds it. Any otea call of the holder keeps its live leases: one with less than half of it left is extended to a full lease from then. An expired lease reads as free and can be taken over, except while its holder's session runs (an MCP server or `otea wait` of it still runs), since the holder may be on a long step with no call, such as a rebase or a test run: then `otea claim` refuses it with exit 12 (`lease_held`), `otea next` does not offer it, and the person frees it on the desk (Liberar). Moving an item off the agent turn (for example to `review`) releases it automatically. On a published board a lease is for one step: every move (a handoff to the next step or to a review, an approval, a send-back) releases it, even when the next step is the agent's too, so it never blocks that step or reads as someone working there; an agent that goes on with the next step claims it again. While another agent holds an item, `otea show` and `otea next` for it say `Held by <agent> until 2026-11-12 10:04 UTC: pick another item.` instead of the agent's turn. Items nobody claimed stay writable, and the human in the web UI is never blocked by a lease. Every agent command acts as a named agent: `--as <name>`, or `$OTEA_AGENT`. Reading (`otea list`, `show`, `events`, `board`) needs no name: without one it reads as the person, and is not recorded as an agent. There is no default name: a command that acts, without one, fails with exit 2 (`unnamed_agent`) saying how to name yourself. The one exception is `otea create` at a terminal: when stdin and stdout are both a terminal and no name is given (no `--as`, no `OTEA_AGENT`), the item is recorded as the person's, with no agent registered and nothing for `otea whoami` to hand out, and its `created` event carries `via: terminal`, shown as "created from a terminal" on the desk, in the feed and in `otea show`. A terminal does not prove a person typed (an agent can be given a pty by an editor's terminal, tmux, `script`, `docker run -t` or `ssh -t`), so the mark is how that create stays distinguishable from one made on the desk. Nothing that decides for the person runs unnamed, terminal or not: `otea answer`, `approve` and `send-back` still fail with `unnamed_agent`, and the person answers, approves and sends back on the desk. The name follows the rule below (exit 6, `invalid_agent_name`) wherever it is given. The name is the agent's identity, so each agent working at the same time uses its own; two agents under one name share every lease. Only items whose turn is the agent can be claimed (exit code 4, `not_claimable`, otherwise). An agent sets aside an item it holds, or one nobody holds since it let it go, as when the person wants it for later, with `otea release <id> --later` (a `released` event with `cause` `later`, read as `(set aside for later)`): `otea next` and `otea wait --unclaimed` then leave it out for every agent, as the person's wish, until the item moves, an agent claims it again, or the set-aside lifts: on its own once what the item waited for (its parts, what blocks it) closes, and whenever the person acts on it (a note, an answer, picking it in the Matrix order, «Poner arriba», or «Retomar» on its page, `POST /api/items/:id/resume`), each written as a `set_aside_lifted` event saying why (`/api/items` gives `setAside` with who set it aside, and when, until then). `otea next` with nothing to do names what is set aside and by whom, with the place of the first of them in the person's order. `--later` is refused with exit code 4 (`children_open`, `blockers_open`, `not_claimable` or `item_closed`) on an item that is not agent work right now, one that waits for its parts, what blocks it or the person, as `otea next` offers it again on its own once it is. It is also refused (exit 4, `invalid_transition`) while a note from the person on the item waits for an answer, giving the `otea reply`, and once the person took the item up again (their act lifted a set-aside) and it has not moved since: `otea next`, `otea show` and `otea wait` then say `The person took it up again (Retomar, <time>): do it now.`, and only the person's newer words, relayed with `otea release <id> --later --quote "<the person's words>"`, set it aside again. `otea wait` gives the person's unanswered notes on the item it wakes for in their words, with the reply. When `otea next` or `otea wait` offers an agent the item it let go of with a plain `otea release`, they add how to set it aside instead.

A lease that ran out without a release leaves its item stuck (**Atasco** in the web UI). There the person either puts it back in the queue of its step for any agent to claim (**Retomar**, `POST /api/items/:id/restart`) or leaves it for a named agent (**Reasignar**, `POST /api/items/:id/reassign` with `{"agent"}`). Both drop the lease that ran out and write a `released` event by the human with `cause` `restart` or `reassign` (and `next`, the agent it is left for); `otea show` reads them as `(back in the queue)` and `(left for <agent>)`. The agent named is expected, not enforced: any agent may still claim the item, but `otea next` offers it only to that agent, and `otea show` tells any other `Left for <agent>: pick another item.` (and that agent `The person left it for you.`) until an agent claims or moves it. An item whose lease is still running, or that has none, is refused (409, `not_stuck`). While its toast is up, `POST /api/items/:id/undo` with `{"release": true}` gives the lease back as it was (with `{"from"}` it takes back a move, as before); like moves, these writes need the session, JSON and the server's own origin.

`otea update` changes fields of an open item (a blank value clears an optional field) and records the old and new values in the timeline; items in a closed state (turn `none`) cannot be updated. A long or multi-line value comes from a file with `--field-file "<name>=<file>"`, or from stdin with `<name>=-` (`otea create` takes it too); a UTF-8 BOM and the line break that ends the file are left out. `--description` fills the board's description field where it has one (Descripción on Errores); a board without one (Cambios) refuses it. Agents act through the CLI, so it only makes the moves a board gives agents. Approving a step the person reviews (`Hacerlo (en revisión)` -> `Integrar` on Encargos; a review reads in the board's language, and `(in review)` is accepted too) is the person's, in the web UI: `otea approve`, `otea move` and `otea relay` refuse it with exit code 7 (`forbidden`).

A board is named in any case wherever a command takes one (`--collection encargos` is Encargos, and so is `otea board encargos`), as its steps and fields are in `otea list --state/--field`: board names are unique whatever their case.

## Relaying a decision made in conversation

The person's decisions on a board that cannot be undone or are theirs alone never go through an agent: a relay never drops, finishes or approves an item (`otea relay ... Dropped` exits 7, `forbidden`, in review or not, with a secretary or without). The person drops with their own tap, on the desk or on the secretary's card (`otea say --drop <id> --note "<why>"`), and can reopen the discard from the desk (Reabrir). What a relay can still do is move an item for the person without closing it, such as sending a step they review back to doing (with no secretary), or accepting a bug triaged as reported:

```sh
otea relay BUG-3 Accepted --quote "Yes, take that one" --as claude
```

- The `--quote` has two words at least. With a secretary, only the secretary relays, with `--from-message <id>`: a message the person wrote in Talk in the last 24 hours (not a tap on an option), that contains the quote, and backs one relay of an item. An item that waits for the person's review is never relayed with a secretary: it asks them with a card.

### What Otea stops, and what it cannot

Otea stops an agent that misuses Otea's own interfaces, the command line and MCP: an invented quote, a name that is not its own, a decision that is the person's. It cannot stop a local process that writes the SQLite file directly: anything running as you on this computer can. For what Otea cannot verify, it makes it visible instead:

- A name is bound to the harness session noted for it (the process above the shells that ran its declaration, claim or wait, with when it started; for MCP, the server and its launcher). While that session runs, the secretary's acts (`say`, `relay`, `conversation`, `create`, `update`, `ask`, `bandeja take|close`, `wait --secretary`) and a worker's acts on an item its own session leased are refused from another session (exit 7, "runs in another session"), over the command line and over MCP. The secretary's declaration (`otea profile --role secretary`) notes its harness, and a wait from another live harness never replaces it. Sessions that declare the same new name at the same moment find one winner, as sessions that wait together do: the others exit 7 ("declared by another session") and keep nothing of their declaration. `otea whoami` and the desk's secretary status say which session is the secretary (`session <pid>`). Once the session is gone, a new one takes the name over.
- While an item waits for the person's review, no agent changes its request or the fields handed in, whatever name it runs under: `otea update`, a checklist tick and the MCP `update` exit 7 (`forbidden`, "waits for the person's review"), and the secretary is pointed to its send-back card (`otea say ... --send-back <id>`). The person edits it on the desk, or sends it back, and the worker changes it then; the desk still marks a request changed after delivery when the person's own edit did it. An agent's own review (a step another agent checks) is not the person's and is not held, and neither are the fields a board takes at any time (its estimates, `anytime`, such as Changes' impact and effort), which an agent still fills. The files of the delivery are held the same way, on any step: `otea attach` and `otea detach` (and the MCP tools) by an agent exit 7 with the same message while the person's review is open; the person attaches on the desk.
- While the secretary's noted session runs, a caller that cannot be proven to be it is refused for every act, not let through: a background process whose parent is gone (no harness resolves from it) and an MCP server whose launcher cannot be resolved count as unproven. A name called through an MCP server that is not the noted session is not heard at all: it moves no binding, listening or harness note, so one impostor's message leaves the real secretary verified and connected.
- When Otea cannot tell (nothing trusted is noted, the process table cannot be read in 3 seconds, the noted harness cannot be resolved, the harness is not one Otea knows by name), the command goes on and the secretary's message is marked «sin verificar» on the desk. An unverified message never carries a card: `say --drop` and `--send-back` are refused, since the person's tap would do what a process of unknown origin drafted.
- A relayed decision is always shown as relayed, with its quote and the message it came from.

- The move is recorded with `via: <agent>`, `source: conversation` and the quote. Otea cannot check that the person said it, so it is always shown as the agent's word and never as the person's own decision: `otea show` reads `relay:claude ... relayed by claude, quoting "<quote>"`, the desk's history, rounds and phone review say `relayada por claude, citando "<quote>"`, and it never counts in Your turn's «aprobaste» or «devolviste».
- A board can turn relay off (`"relay": false` in `board.json`; on by default). On it, `otea relay` and the MCP `relay` tool exit 7 (`forbidden`) telling the agent to ask the person with `otea ask <id> "<question>"`, and `show` offers no relay.
- `--quote` is required and cannot be blank (exit 2, `quote_required`). When the transition requires a reason, `--reason` is required too (exit 2, `reason_required`): the quote is evidence of the approval, the reason is the same field the UI records, and a quote such as "yes" explains nothing.
- An approval that lands on main or closes the item cannot be relayed: on a board, the person's forward approval into a land step or Hecho (every shipped board, Content's publish and Design's land included) is `human-ui`, so `otea relay` exits 7 (`forbidden`) saying the person gives it on the desk or the phone, and `show` does not offer it; ask with `otea ask`. Send-backs (`Devolver`) stay relayable where there is no secretary; drops never are. A send-back is relayed only while the person reviews the step: on an item still in its agent's hands (`Hacerlo`, not `Hacerlo (en revisión)`) `otea relay` exits 4 (`invalid_transition`) saying the item is not in review and that it reaches review when its agent hands it off. `otea answer` and `otea release --later --quote` carry the person's words the same way: a board with `relay` off refuses them too. Moves an agent may make itself are refused with exit 4 (`not_relayable`): use `otea handoff` or `otea drop`. Unknown items and undeclared moves fail as usual (exit 3, exit 4).
- An agent never relays a decision on its own work: once it has done the item's step in the current round (handed it off, or, while the step was being done, claimed the item, attached evidence or changed its fields, even if another agent handed it off; off a board, once it made the move that brought the item where it is), every relay of it by that agent exits 7 (`forbidden`, details `own_step`); the person decides in the web UI.
- A relayed decision is the human's, so like a move in the UI it is not blocked by another agent's lease; moving off the agent turn releases that lease as usual (the release is marked as relayed too).

## Waiting for work and following events

An agent does not have to poll `otea list`: `otea wait` blocks until there is work, and `otea events` reads what happened. Both work across processes without `otea serve`.

```sh
otea wait --turn agent --unclaimed --timeout 15m --json   # then: otea claim <id>
otea events --since 42 --json                              # events after id 42, one JSON object per line
otea events --item TAR-1 --follow                          # keep printing new events until Ctrl+C
```

- `otea wait --turn agent|human` returns at once when an item is already on that turn, otherwise as soon as one gets there. It prints the item as a row of `otea list` (with `--json`, one object shaped like an entry of `otea list --json`). When several match, it prints the one that has waited longest: the first to enter its current state (field updates and leases do not reset it), ties going to the first created.
- `--collection` narrows it and `--unclaimed` skips items another agent holds, as in `otea list`; a lease that expires frees its item for the wait without anything being written. Without `--unclaimed` the wait is a view of the turn, so an item another agent holds wakes it at once; it then says who holds the item and until when, and gives the `--unclaimed` command that waits only for work the agent can take (the one `otea next` and the guide give). `wait` only reads: claim the item afterwards with `otea claim`, and if that fails with exit 12 because another agent got there first, wait again.
- `--timeout <duration>` (`600`, a number of seconds; `600s`, `10m`, `1h`) gives up with exit 13 (`timeout`: nothing is wrong, the wait only ran out: wait again); without it, `wait` waits until interrupted (exit 130, `interrupted`). An agent stops its own wait by ending the shell that runs it or with `--timeout`, never by killing processes by name or pattern, which can stop another agent's.
- A wait ends with the shell that started it, by design: left running it would keep its agent shown as listening for nobody. So `otea wait &` inside a short command, or in a subshell that returns, ends at once with `Stopped waiting: the session that started it ended` (exit 130). Run it as the harness's own background task or shell, which lasts as long as the session, and start it again from there if you read that line.
- Only a running wait hears the desk: the person's approvals, answers and notes reach an agent that is in `otea wait`, and `otea next` with nothing to do says so. Over MCP its last line gives the wait first as a background shell line, which keeps the chat free, and the `wait` tool second, since it holds the chat until it returns. The guide tells an agent to go back to waiting after it answers the person in the chat.
- A harness that runs its sessions in a background service (OpenCode's, for one) can keep an agent's background `otea wait` alive after you close the harness's window: when the wait returns, the service resumes the session and the agent works on with no window open. End the session in the harness, or that wait, before you close the window.
- Every text of the CLI and the MCP tools says a time one way, as its UTC day and minute: `2026-11-12 10:04 UTC` (a lease, an event, a refusal). `--json` keeps the full ISO timestamp.
- `otea events` prints the event log in commit order, filtered by `--item` and `--collection`. Each event has an id; pass the last one you read to `--since` to get only newer ones. `--limit <n>` alone reads the latest n; after `--since` it reads the first n after it. With `--json` each line is an event shaped like the ones in `otea show --json` (`id`, `itemId`, `type`, `actor`, `at`, `data`). On a board, whose steps and fields are stored under hidden ids, the text names them, and `--json` gives each id its name beside it (`stateName`, `fromName` and `toName`, `moduleName`, and a `name` on each field change). Items read the same way in `--json` and MCP: `stateName` beside `state`, `fields` as a list of `{ id, name, value }` (a choice also has its `label`), and each move's `toName`; the ids stay the keys a program sends back. `--follow` keeps printing new events as any process commits them, until Ctrl+C (exit 0); it cannot be combined with `--limit`.

## Telling agents what to do

An agent finds its instructions in the project itself, in the words of each board:

```sh
otea next                             # the item to take now and what its step asks
otea next --claim                     # ... and claim it in the same call
otea board                            # the project's boards, each with the command that reads it
otea board Errores                    # that board's own words for agents and each step's instructions
otea show ERR-2                       # ... Next: the same answer as otea next, for this item
otea init --agents-md                 # opt in: point agents at "otea next" and "otea board" from AGENTS.md
```

- `otea next` says which item to take now on the published boards (or in `--collection`), and what its step asks: what it starts with, the instructions, the handoff and where it goes next. The order: what the agent holds, what the person left for it, then items sent back to it, then what the person put on top (`Poner arriba`), then approved work (the step began with a review's approval, read from the item's events, not from where the step stands: on a board whose second step is the person's, a bug they triaged is new work) before new work, and inside each of those two the order the person fixed on the Matrix, then the oldest. A new item the person ranked first never goes before returned or approved work. Every reading is whole; `--brief` on `next` and `show` is for the repeat read of an item the agent holds and already read in this session: it leaves out the board's words, the step's `Before you hand it off` and the checklist lines already met, and ends with where the whole is (`otea board <name>`). An item nobody holds says `Claim it first: otea claim <id>`; one the agent holds says until when. `--claim` claims the item in the same transaction (`lease` in `--json`), so two agents asking at once never take the same one. Without it, the item offered is kept from other agents for two minutes while it stays in its step, so they are offered another, and `next` says so: `Offered to you for 2 min, not claimed` (an agent that only looks takes the item out of the others' reach for that long); an item another agent holds is never offered. `--model` and `--effort` on `next` (with `--harness` the first time, on the command line) declare the profile first, as `otea profile` does, so a subagent needs one call, not two. Each value under `Starts with` is given whole, line by line; one over 500 characters is cut there, with the `otea show` that reads all of it. When there is nothing to take it says so once, naming the boards, with each board's own words for idle time, and how to wait for the next item (`otea wait --turn agent --unclaimed`). A `--way` the step does not have is refused (exit 4, `invalid_transition`) with the ways it has: on to a later step or Done, and back to an earlier step with `--reason` (`ways` and `back` in the error's data).
- Otea's agent guide, a few numbered lines on working a board to the letter (name yourself with `--as`, a unique name per agent and subagent; declare the model and effort you really run as with `otea profile`, each session and whenever either changes; start with `otea next`; claim each step before working it; follow the step's instructions and every line of `Before you hand it off`; answer a `Sent back to you` note; hand off with the command `next` prints; never relay a decision on your own step; never push to a branch the item does not allow; answer every note from the person before handing off; only the project's secretary talks with the person in Talk, everyone else asks on the item), is one text that reaches each agent once, as it stands now: an MCP agent reads it in the server's `instructions`, and any other agent (or one whose client shows no instructions) at the start of `otea board`'s index, where the `AGENTS.md` block sends it. A single board's text and `--json` leave it out, and the `AGENTS.md` block holds no copy of it, so it is never in context twice and never goes stale.
- `otea board <name>` prints what agents read about a board before acting: its own words for them and each step's instructions (`--json`: `kind`, `collection`, `board`, `version` and `text`). A board that is not published yet fails with exit 3 (`not_found`). Without a name it prints the index (`--json`: `boards`, each with `name`, `board`, the board's id or `null` for a draft, and `command`; a name with spaces is quoted).
- `otea show` (and `--json`, as `hint`) carries `Next:`, the answer `otea next` gives for that item on its board: whose turn it is, what the step starts with, what the handoff still lacks and where it goes next. A long board text is cut to its first paragraph there, with the `otea board` command that reads the whole of it.
- `otea init --agents-md` adds a short block between `<!-- otea:begin -->` and `<!-- otea:end -->` to `AGENTS.md` at the project root (creating the file if needed) saying where Otea's agent guide is: the MCP server's instructions, or else `otea board` (the `board` tool with no name), read first; then `otea next`. It holds no copy of the guide. Running it again replaces the block, never duplicates it, and leaves the rest of the file alone. `otea init` alone never touches `AGENTS.md`.

## The profile an agent runs as

Every agent, and every subagent, declares the profile it runs as: its harness, its model and its effort. It is kept on everything the agent does, so rounds and send-backs can be compared by model and effort afterwards; it never decides who gets which work.

```sh
otea profile --model claude-opus-5-5 --effort high --harness claude-code   # the first time on the command line
otea profile --effort max                                                  # one value changed: the rest stays
otea profile                                                               # what is on record (--json too)
```

- `--model` is the exact model id and `--effort` the effort, both as the harness names them, stored as given (one word each, at most 100 characters; else exit 2, `invalid_profile`). There is no translation between vendors: `--json` adds a `family` that groups model ids (`opus`, `sonnet`, `haiku`, `gpt-5`, `o3`, `gemini-pro`, ...; an id it does not know is its own family).
- Declare what this session tells you (your instructions, or what the person says); never open config files outside the project for it. Otherwise declare `unknown` (`--model unknown`, `--effort unknown`, any case; stored as `unknown`). Never guess. It still makes a profile, and `otea stats` and Rendimiento keep it as its own group, never inside a family, after the declared rows (shown as "not declared"). The harness takes no `unknown`: an agent always knows the tool it runs in.
- The harness an agent names is the harness: `--harness` on the command line (the first time, kept after that), `harness` on the `profile` tool. When it names none, the MCP client's name in its initialize (`clientInfo`) is the harness (a profile that came from `otea connect` with no `--harness` reads `cli` until the client names itself). A name the agent declared stays over `clientInfo`, whether it declared it before or after its client was first heard, so several agents behind one client (a script, a bridge) each keep their own. The desk's agents menu still shows the client an agent was heard through.
- `otea claim` refuses an agent with no profile, and `otea next` one with no profile or one not declared in this session, with exit 2 (`profile_required`) and the exact command that declares it. A session starts when an MCP client initializes the server, at the first call of each agent name on that server, and, on the command line, when an agent comes back after an hour unseen: until it declares its profile again, the profile stands unconfirmed.
- Every `otea next` ends with `Your profile: <model> · <effort>. If you changed model or effort, update it: otea profile …`, and `--json` carries it as `profile`.
- Every event an agent writes keeps the profile it had then (`profile` on each event in `otea events --json`, and in the web server's events; the person's events have none, and a relayed decision keeps the relaying agent's). The profile a round counts is the one on its handoff. Each change of profile is kept too, in its own append-only history.

How each model performs, from those profiles: `otea stats` prints one row per model family and effort (the exact models and each board's steps under it) with its handoffs, how many came back for another round (sent back), the rounds a finished step took on average, the items done it handed off part of, the items discarded after its last handoff, and the median time from claim to handoff. A finished step counts for the profile on its last handoff; steps the person did and agents with no profile are left out. `--since 7d` (or `30d`, `12h`, `all`, the default) keeps a period and `--board <name>` one board; `--json` gives the same numbers. The web page shows them in Rendimiento (Performance), reached from the agents menu and the rail. The profiles are as the agents declare them: Otea does not check them.

```sh
otea stats --since 30d                                     # per model family and effort, last 30 days
otea stats --board Errores --json                          # one board, as JSON
```

## The canonical way: a secretary, workers and a refiner

One chat, the **secretary**, talks with you and keeps the work moving; **workers** do the items; a **refiner** turns your rough notes into items; and you decide on the desk or the phone. Otea never launches an agent: your harness launches them. What Otea does is show when the secretary is away or nobody is listening on a board, tell you, and make review fast.

The roles:

1. **Secretary**: one per project, in your own harness session. It declares itself (`otea profile --role secretary`) and listens with `otea wait --secretary` in the background, running it again after every action: it wakes for a message of yours in **Talk** (the desk's and the phone's chat with it), a note in the **Inbox** (your rough captures), an item that reaches your review (`ready_for_review`: it tells you in one line with the item's link, a second round after a send-back too) and a board with work and nobody listening. It reads with `otea conversation`, and answers a message of yours with `otea say --reply-to <id>`; its own news (an item ready for your review, something that went wrong) is a message with no `--reply-to`, which stands at the foot of the thread, in the order things were said, and never changes how your messages are sorted. It sorts each message of yours: a **request** becomes items (`otea create --from-message`, with What I want and How I check it filled in, so they skip the clarifying step) that `say --request --links` ties to your message (an item born from an Inbox note is never tied to a message); a **consultation** (a question, advice, an explanation) is answered and saved with `say --consultation`. When it is unsure it asks you with `say --option … --recommend n`, which shows as buttons you tap (what you chose stays in the thread), and you correct a kind with one tap: that wakes the secretary, which acts on it at once. It keeps one worker per board with work (a second on its own when a code board has two or more items waiting: `otea pending` says it) and a refiner for the Inbox running, and it never takes, claims or hands off an item, approves or sends back for you, or relays your decisions: doing work would block the chat you talk to. It says what is true now: a request it queued reads "queued as CAM-3; a worker takes it now", never "done", until the item is Done.
   When you change your mind about an item already made, it reads the item first. Not in your review yet, it changes it and tells its worker in one act (`otea update <id> --field … --tell "<what changed>"`: the worker hears it at once, even mid-step, as a note it answers before it hands off), and it deals with your message before any new request. In your review, it never changes it under you and never sends you to the board: it puts a card in Talk (`otea say … --send-back <id> --note "<your change>" --option "Send it back" --option "No"`) and **your tap** sends the item back as you, with that note, which you can edit first; the secretary cannot do it, and cannot leave that decision to itself.
   It answers short: the first line is the conclusion, in one sentence, then at most three short lines; anything longer goes in a file (`otea say --file`) or on the item, and a question to you always has two to four options and says which it recommends. The desk keeps to the same rule: a reply past a line and three short ones folds behind «ver más».
2. **Worker**: one per board, at most two on a code board. It has a fixed name and loops `otea next --collection <board> --claim`, does the step, hands off with the exact command and runs `otea next` again; with nothing left it runs `otea wait --turn agent --unclaimed`. It works in its own git worktree, inside the repository, at `.otea/worktrees/<item id>` (scratch files in `.otea/tmp/<item id>/`, never beside the repo or in the temp folder; your main checkout only where a step says so), and lands approved work with a merge of main, never a force push. When what landed is on the remote's main but your local main is behind, the handoff and the item say so, and the worker runs `otea land sync <item id>`, which fast-forwards your checkout's local base (the board's protected branch, to the remote it is pushed to) only when that checkout is on it with no change to a tracked file, and says why when it leaves it alone; the worker never runs git pull or merge in your checkout itself. On Windows in Git Bash it sets `MSYS_NO_PATHCONV=1` and writes paths as `D:/folder`, never `/d/folder`. It never decides for you and never stops silently: it asks on the item with `otea ask`, with options. A worker never writes in Talk: only the secretary does.
3. **Refiner**: it turns the Inbox's notes into proper items. There is one for the whole Inbox, and it stays: it takes the next free entry, waiting for one when none is (`otea bandeja take --next --wait --timeout 90s`, run again at once on a timeout: a wait over two minutes is moved to the background by some harnesses, and a refiner that ends its turn then is gone), reads it whole, files it on the right board with What I want and How I check it (`otea create --from-bandeja`), and, when something is missing, asks you on the entry with options (`otea ask <B-n> --option ...`), then goes on with the next entry; your answer frees the entry and the same wait gives it back to it. A duplicate, or a note that needs no item, is closed with its reason (`otea bandeja close <B-n> --reason "..."`, the secretary's or the refiner's); the desk shows "cerrada: <reason>" and you can reopen it.
4. **You**, on the desk or the phone: talk in Talk, approve, send back with a note, answer questions, and capture with **Nuevo ítem** (a note for the Inbox, or an item straight onto a board). You never relay between agents.

**Approvals that overlap.** Items whose pushed branches change the same files used to be approved together, landed one after the other and each landing conflicted with the one before: a bounce back to your review, again and again (field studies 4 and 5). Now, when you approve an item that overlaps another one that is approved and not landed yet (or is landing, or is back for the review of its own merge), the item does not go to an agent yet: it waits as «aprobado · espera a X» (_approved · waits for X_) on the board row, the item page, Te toca, Hablar's chips and the phone, and `otea pending` and the secretary's texts say the same. When X lands, the item's agent merges main into it first (the worker's `otea next` and `otea show` say which items landed ahead; a closing handoff is refused until then). If the merge is clean and the checks pass, the item comes back to your review once, as a merge-only round that shows only the merge; if it conflicts, the agent resolves it and it comes back once with the resolution. You never see «volvió por un choque» for items approved together. Three items in a chain wait in line: each waits for the one ahead of it, also while that one is back for its merge review, so none lands past another and returns. If X is sent back or dropped after you approved the item, the item is released to land like any other. Items that share no file behave exactly as before.

Each role has a text to paste, in the project's language (or `--lang`), the same one the desk serves from `GET /api/agent-prompt?role=<secretary|worker|refiner>&board=<name>&as=<name>`:

```sh
otea prompt --role secretary                                    # paste into the chat you talk to
otea prompt --role worker --board Cambios --as ana-cambios      # one worker of the board Cambios
otea prompt --role worker --board Cambios                       # without --as it tells the worker to pick its name with otea whoami
otea prompt --role refiner                                      # the refiner of the Inbox
```

`--role coordinator`, the name of the secretary's text before 0.8, is gone, with no alias.

How Otea tells who is there. The secretary reads **offline** within seconds of its session ending, not after the thirty minutes it is otherwise held for between two waits: its `otea wait --secretary` notes the harness process above the shells that run it (the program that lasts as long as the session), and a secretary whose wait, MCP server or harness process is gone is offline at once; the desk learns it with no other change (the server looks every two seconds while a desk is open), and the notice says how to bring it back (`otea wait --secretary --as <name>` if its session is open, else paste `otea prompt --role secretary --as <name>` into a new one). A project with a secretary keeps one live worker per board (two on a board that protects a branch): a worker that holds an item of the board on a live lease, or handed one off or let it go in the last five minutes while still connected, counts, a second worker's `claim` or `next --claim` on that board is refused saying who is there, and neither the secretary's wait nor the push «nobody is listening» is told for a board with a worker at work. A holder reads **working** until half a lease (7.5 minutes) passes with no sign of it, and only then «sin señal»; the person's answer to its question renews its lease if it was about to run out. Answering a message with `otea say --reply-to` marks that message read, so the next `otea wait --secretary` does not bring it back.

Launch them one of two ways. The way of working is the same:

- **Background subagents**, where the harness has them (Claude Code, opencode, Cursor): paste the secretary text into your chat. It launches each worker and the refiner as a background subagent with their texts as instructions, and launches a worker again when the secretary's wait says a board has work and nobody listens; the refiner is launched once and keeps running.
- **No subagents** (a harness that cannot run them in the background): the secretary does not do their work in your chat. It tells you, in one numbered message, exactly how many other sessions to open (one chat or terminal per board with work, plus one for the refiner) and pastes under each number its full text, the output of `otea prompt --role worker --board <name>` and `otea prompt --role refiner`. Until the refiner session is open it refines the Inbox itself, the way the refiner text says (it takes each note under its own name, never for a refiner that is not running: a note taken for one comes back to it after a few minutes if that refiner never calls otea), and it goes on listening.

First contact is not "design a board from scratch": the agent that sets up a project (`otea prompt start`) first asks what work you want agents to do, what "done" looks like, who reviews and where it lands, one question at a time, and then says plainly one of four things: a stock template fits as it is, a template fits with these changes, this needs a board of its own (drafted with `otea board draft`), or Otea is not a good fit (for example, one-off tiny tasks are faster in plain chat).

## What to paste into an agent's chat

`otea prompt` prints what the person pastes into an agent's chat, the same text the UI copies (**Conectar un agente** and the empty project page), in the project's language (fixed when the project was made, in the language you used then; `otea projects lang` changes it) or with `--lang`:

- `start`, the first contact on a new project: set it up (`otea init`, no template) and connect (`otea connect` with the agent's own name, model and effort), read the project (README, code, git history, CLAUDE.md or AGENTS.md, CI; in a folder that is no git repository, what is in it, with no git words), understand what the person needs one question at a time, say plainly which of four outcomes fits (a stock template as it is, a template with changes, a board of its own, or Otea is not a good fit, in which case it drafts nothing), draft the boards with `otea board draft --new … --why … --template <key>`, say where to review them and to try them with a first item, and then keep working.
- `--role secretary`, `--role worker --board <name> [--as <name>]` and `--role refiner [--as <name>]`, instead of a moment: the canonical texts of [the secretary, its workers and the refiner](#the-canonical-way-a-secretary-workers-and-a-refiner). A worker needs its board (the others take none); only a name given with `--as` is filled in, never the session's own.
- `join`, one more agent on a project that has boards: pick a name none of the listening agents has (they are named), connect (`otea connect`, which writes nothing that names it) and put the name on every command, declare its profile, read the guide and the boards, written from the project as it is now (each board's agent steps and how many items wait for an agent), and work the queue (`otea next --claim`, hand off, `otea wait`), never taking an item another agent holds and never designing boards.
- `design`, one more board on a project that already has some.

Without one, it gives `start` until the project has a board of its own (or where there is no project yet), then `join`. `GET /api/agent-prompt?kind=&lang=` answers the same for the UI, and `?role=` (with `board=` and `as=`) the role texts.
